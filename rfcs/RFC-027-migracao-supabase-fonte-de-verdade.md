## Descrição
Inverte a arquitetura de persistência do PolvIn: hoje o `localStorage` é a fonte de verdade e o Supabase é uma sincronização opcional e best-effort (`js/cloud.js`); a partir desta RFC, toda conta passa a ser obrigatória (e-mail/senha ou Google, via Supabase Auth), o Supabase (tabela `user_data`, `supabase/schema.sql`) passa a ser a fonte de verdade dos dados, e o `localStorage` passa a ser só um cache local de leitura/escrita otimista. Não há mais um "modo 100% local" como caminho de produção.

## Objetivo
Garantir que qualquer pessoa que use o PolvIn tenha seus dados (progresso, XP, transações, investimentos, conquistas etc.) disponíveis e corretos em qualquer dispositivo em que fizer login, eliminando o modelo atual em que dados "vivem" no navegador e a nuvem é um espelho opcional e desatualizável.

## Motivação
Decisão de produto do usuário: o PolvIn deixa de ser uma ferramenta single-device e passa a assumir que o público real usa celular e computador para a mesma conta. O modelo atual ("100% funcional sem conta") foi correto enquanto o Supabase era experimental; deixou de refletir a direção do produto.

## Benefícios
- Continuidade real entre dispositivos (hoje é uma "limitação honesta" documentada, não uma feature).
- Base necessária para qualquer coisa que dependa de identidade estável de usuário no roadmap já existente (ex.: "Ranking/Ligas ao vivo", item 1 do "Roadmap sugerido" do README).
- Simplifica o modelo mental do produto: uma única fonte de verdade, não dois caminhos (local vs. nuvem) para QA/documentação sustentarem para sempre.

## Impacto
- **Boot da aplicação** (`js/app.js`): `App.init()` hoje faz `Cloud.init()` → `ensureVaultUnlocked()` → renderiza tudo, sem nenhum gate de conta. Precisa de um novo gate bloqueante de autenticação, posicionado **antes** de `Cloud.init()` decidir o que hidratar — arquiteturalmente análogo ao padrão que já existe em `ensureVaultUnlocked()` (uma Promise que só resolve quando a condição é satisfeita, com tela cheia bloqueando o resto do boot).
- **`js/auth.js`**: hoje tem 3 ramos (conta cloud real, perfil local por e-mail sem senha, perfil local Google "decorativo"). Os dois ramos locais deixam de fazer sentido como estado final — todo `getAccount()`/fluxo de criação de conta converge para `Cloud`. `STORAGE_KEYS.ACCOUNT` fica obsoleto como conceito de identidade.
- **`js/cloud.js`**: `syncOnLogin()`/`pushAllLocal()`/`hydrateLocalFrom()` já cobrem o caso "nuvem vazia → sobe local" e "nuvem tem dados → substitui local", mas sem sinalizar ao usuário antes de sobrescrever.
- **`README.md`**: várias afirmações centrais ficam falsas ("Funciona 100% localmente... sem nenhuma conta", Supabase listado como "(opcional)") — reescrita pelo Documentation Specialist ao final.
- **`supabase/schema.sql`**: nenhuma mudança de schema estritamente necessária para o modelo genérico chave/valor (ver detalhamento do Product Owner abaixo) — mas ganha uma dependência operacional: precisa estar de fato aplicado num projeto real antes de deploy de produção.

## Dependências
1. **Projeto Supabase real e completo** — hoje `SUPABASE_URL` está em branco em `js/supabase-config.js` (`Cloud.isAvailable() === false` neste momento). Bloqueador de publicação, não de escrita desta RFC.
2. **Recuperação de senha (novo requisito de MVP)**: não existe hoje nenhum fluxo de "esqueci minha senha" no código (confirmado — sem chamada a `resetPasswordForEmail`). Aceitável quando conta era opcional; inaceitável como único caminho de acesso aos dados. Entra como requisito de MVP desta RFC.
3. **Decisão "Confirm email" ligado/desligado**: cabe ao Security Specialist decidir com input de produto (cadastro sem fricção vs. segurança de dados financeiros).
4. **Exclusão de conta completa (LGPD)**: apagar a credencial em `auth.users` exige a `service_role key` (nunca pode chegar ao navegador) — provavelmente uma Supabase Edge Function pequena, infraestrutura nova. Registrado como risco para Security/DevOps avaliarem; não é MVP desta RFC, mas precisa constar no roadmap se ficar de fora.
5. Sequenciamento com a Cidade Financeira — resolvido, ver nota acima.

## Critérios de aceite
1. Usuário novo não consegue usar nenhuma aba/funcionalidade do app sem antes criar conta (e-mail/senha ou Google) — gate de autenticação bloqueia o boot antes do onboarding.
2. Usuário com dados só locais que cria conta pela primeira vez tem 100% das suas `STORAGE_KEYS` existentes replicadas no Supabase logo após a criação de conta, sem ação manual de "sincronizar".
3. Em colisão (conta já tem dados na nuvem ao logar num dispositivo com dados locais também), o app NÃO apaga silenciosamente o lado mais rico — mostra aviso explícito antes de qualquer substituição.
4. Login num segundo dispositivo traz os dados da conta corretamente; qualquer sobrescrita de dado local é comunicada ao usuário, nunca silenciosa.
5. Instância sem Supabase configurado não se comporta como "modo local completo" — mostra tela explicando que não está configurada para uso real (distinta de erro genérico).
6. Perda de sessão/token inválido durante uso normal nunca trava a tela nem interrompe ação em andamento; leitura continua via cache local; falha de escrita gera indicador visível + forma de tentar de novo, sem exigir reload.
7. Fluxo funcional de "esqueci minha senha" (e-mail via Supabase Auth) acessível a partir da tela de login.
8. `README.md` deixa de descrever Supabase como "opcional" e o app como "100% local, sem conta".
9. Nenhuma funcionalidade de gamificação (energia, streak, XP, conquistas, Cidade Financeira) perde integridade de contagem por sincronização malsucedida ou fora de ordem — validação específica em QA para `CITY_LIFE`, `XP`, `STREAK`, `ENERGY`.

## Registro por etapa

### 1. Product Owner
- **Resumo da etapa**: Mapeado o código atual (`storage.js`, `cloud.js`, `auth.js`, `vault.js`, `supabase-config.js`, `app.js`, `schema.sql`). Infraestrutura de sync já cobre parcialmente o caso mais comum, mas tem lacuna real no caso de colisão (nuvem sempre vence, hoje sem aviso).
- **Decisões tomadas**: conta obrigatória confirmada (não reaberta); recuperação de senha entra como MVP; "nuvem sempre sobrescreve" deixa de ser aceitável sem aviso explícito; app sem Supabase configurado deixa de ser modo de produção válido.
- **Achado técnico chave**: das 41 chaves reais em `STORAGE_KEYS` (não 13), 37 são compatíveis 1:1 com o modelo genérico chave/valor de `user_data` sem mudança de schema. 4 casos precisam de atenção do Software Architect/Database Engineer:
  - `ACCOUNT` (`if_account`): identidade local paralela e mais fraca que a conta Supabase Auth — deve ser **descontinuada como conceito de identidade**, não migrada como está.
  - `VAULT_ENABLED`/`VAULT_SALT`/`VAULT_CANARY`/`VAULT_BLOB`: já sincronizam hoje pelo mecanismo padrão (não estão em `SENSITIVE_KEYS`). Avaliar se o cofre local (2ª senha, nunca enviada a lugar nenhum) ainda faz sentido agora que a nuvem é fonte de verdade.
  - `LESSON_LOG`/`SIMULATOR_LOG`/`POLVIN_LOG`: histórico que regrava o blob inteiro a cada evento — cabe no modelo atual, mas candidato a modelagem por linha-por-evento (não bloqueante).
  - `CITY_LIFE`: chave de maior frequência de escrita do app — a que mais sofre com "nuvem sempre sobrescreve local". Evidência técnica concreta de por que a trava de sequenciamento original fazia sentido.
- **Pendências**: decisão de "Confirm email" (Security Specialist); decidir se existe um "modo desenvolvimento sem Supabase" explícito (UX/UI + DevOps); decidir se "merge inteligente entre dispositivos" (já no ROADMAP) entra nesta RFC ou é sequenciado logo depois (Software Architect); exclusão de conta via Edge Function (Security/DevOps, fora do MVP mas registrar no roadmap).
- **Riscos**: perda de dados reais no cenário de colisão se o MVP não incluir aviso antes de sobrescrever; risco de funil (cadastro obrigatório antes de qualquer valor demonstrado) — UX/UI precisa desenhar o gate sem parecer muro burocrático; risco de LGPD represado se "excluir conta" ficar sem dono.
- **Próximo agente responsável**: Software Architect

### 2. Software Architect
- **Resumo da etapa**: Lidos `js/app.js`, `js/auth.js`, `js/cloud.js`, `js/vault.js`, `js/storage.js`, `js/supabase-config.js`, `supabase/schema.sql` e `index.html` (markup das telas cheias existentes). Confirmado: `.onboarding-screen` (`css/style.css:455`, `position:fixed; inset:0; z-index:100`) já é um overlay opaco independente da ordem no DOM — é o mecanismo certo para reaproveitar em todo gate novo, garantindo zero flash do app atrás. Decisão estrutural central: o boot passa a ter **quatro gates sequenciais, bloqueantes, no mesmo padrão de `ensureVaultUnlocked()`** (Promise que só resolve com a tela cheia escondida), na ordem: (0) Supabase configurado → (1) autenticado → (2) sincronização resolvida (sem colisão pendente) → (3) cofre local desbloqueado (já existente, inalterado).

- **Decisões tomadas** (uma por pergunta do Orchestrator):

  **1. Gate de autenticação obrigatório no boot**
  - Decisão: novo método `App.ensureAuthenticated()`, chamado em `js/app.js` logo **depois** de `Cloud.init()` (que passa a *só* restaurar a sessão — ver decisão do item 2) e **antes** de `ensureVaultUnlocked()`. Mesma forma de `ensureVaultUnlocked()`: `return new Promise((resolve) => {...})`, mostra uma tela cheia nova (`#authGateScreen`, classe `.onboarding-screen`) e só chama `resolve(true)` quando `Cloud.isLoggedIn()` for verdadeiro após um login/cadastro bem-sucedido. Enquanto a Promise não resolve, nenhuma outra linha de `App.init()` roda — os `Xxx.init()` de todos os módulos (Trail, Wallet, City, etc.) ficam depois dele na cadeia, então nada é renderizado com dados ainda.
  - "Tem sessão válida?" é decidido inteiramente por `Cloud`/Supabase Auth (`Cloud.isLoggedIn()` → `!!this.session` após `sb.auth.getSession()`), nunca por uma checagem local paralela — mantém "sessão Supabase = única fonte de identidade" (decisão do item 3) consistente já no boot.
  - Por quê: é exatamente o padrão que já existe e já é entendido pelo time (`ensureVaultUnlocked`); não introduz um segundo mecanismo de "tela de bloqueio" com regras diferentes.
  - Implicação: o formulário de login/cadastro em si **não deve ser duplicado** entre a tela de gate e o modal de conta que já existe em `Auth.openModal()`. Ver item de reuso abaixo (extração de `Auth.authFormHtml()`).

  **2. Fluxo de primeira sincronização / colisão**
  - Detecção de colisão: **binária, sem heurística de timestamp** — "nuvem tem ≥1 linha E localStorage tem ≥1 chave de dado real (excluindo apenas as 4 chaves de metadado do cofre `VAULT_*`) = colisão, sempre avisa". Comparar `updated_at` para tentar decidir automaticamente qual lado "ganha" é exatamente o tipo de decisão silenciosa que a RFC pede para eliminar — qualquer heurística "esperta" aqui reintroduz o mesmo risco de perda de dados só que mais difícil de depurar. Simplicidade > sofisticação neste ponto.
  - Mudança de forma em `js/cloud.js`: `syncOnLogin()` deixa de mutar dados silenciosamente. Novo contrato: retorna um descritor sem efeito colateral quando há colisão — `{ case: "cloud-empty" | "local-empty" | "both-empty" | "collision", rows }`. Nos três primeiros casos (não-colisão), continua agindo sozino exatamente como hoje (`pushAllLocal`/`hydrateLocalFrom`), sem UI nenhuma — só quando `case === "collision"` é que nada é escrito ainda e a decisão sobe para a UI.
  - Novo gate `App.ensureCloudResolved()`, chamado depois do gate de autenticação e antes do `ensureVaultUnlocked()`: chama `Cloud.syncOnLogin()`; se não for colisão, resolve na hora (sem tela, sem flash); se for colisão, mostra uma tela cheia nova (`#syncCollisionScreen`) com duas opções apenas — nada de "mesclar":
    - "Usar dados da nuvem" → nova função `Cloud.applyCloudWins(rows)`: limpa todas as `STORAGE_KEYS` locais (exceto `VAULT_*`) e então aplica `rows` (mesma lógica do atual `hydrateLocalFrom`, mas com a limpeza prévia — sem isso, uma chave que só existe localmente sobreviveria "escondida" mesmo escolhendo a nuvem).
    - "Usar dados deste dispositivo" → nova função `Cloud.applyLocalWins()`: push de tudo que existe localmente (como `pushAllLocal` hoje) **+** apaga na nuvem qualquer chave que não exista mais localmente (senão o "espelho" fica inconsistente com o lado escolhido como vencedor).
  - Por quê duas opções e não três: "merge inteligente" está fora do MVP (ver item 7) — oferecer uma terceira opção de "mesclar" sem uma implementação real por trás seria prometer algo que o sistema não faz.
  - Implicação para a próxima etapa: Database Engineer não precisa de mudança de schema para isso (segue key/value); Backend Engineer implementa as duas funções + o novo contrato de `syncOnLogin()`; UX/UI desenha a tela de colisão (aviso claro, sem jargão técnico, com o "custo" de cada escolha visível — ex.: "isso substitui os dados deste aparelho pelos da nuvem").

  **3. Destino de `STORAGE_KEYS.ACCOUNT`**
  - Decisão: **removida como chave de storage**, não mantida nem como "perfil de exibição". `STORAGE_KEYS.ACCOUNT` sai de `js/storage.js`. Motivo de não manter nem como perfil cosmético: seria escopo novo (nickname/avatar customizável dentro do app, distinto do que vem do provedor de auth) que nenhum critério de aceite desta RFC pede — se o Product Owner quiser isso no futuro, é uma RFC própria, não um resquício desta migração.
  - Mudança de forma em `js/auth.js`: `Auth.getAccount()` deixa de ter dois ramos (cloud vs. `Store.get(ACCOUNT)`) e passa a ter **um único ramo**, sempre derivado de `Cloud.session.user` (e-mail + `user_metadata`) — se não há sessão, retorna `null` (não existe mais "perfil local sem senha"). Consequência direta: `Auth.setLocalAccount()`, `Auth.createLocalEmailAccount()` e o ramo "sem Supabase configurado" de `Auth.handleGoogleCredential()` e de `Auth.openModal()` (hoje linhas ~236–254) são **removidos** — deixam de ter razão de existir porque não há mais estado final "logado só localmente".
  - `Auth.logout()` perde o ramo local (`Store.remove(ACCOUNT)`); fica só o ramo `Cloud.signOut()` + `location.reload()` — o próprio reload já basta para o usuário cair de volta no gate de autenticação (item 1), nenhum código novo necessário para isso.
  - Efeito colateral a corrigir: `js/leagues.js:120` e `js/profile.js:26` leem `Store.get(STORAGE_KEYS.ACCOUNT, null)` diretamente, por fora de `auth.js`. Com a chave removida, ambos precisam trocar essa leitura por `Auth.getAccount()` — centraliza identidade de exibição num único ponto de acesso, em vez de três módulos lendo a mesma chave de formas ligeiramente diferentes.
  - Reuso de UI: o formulário de e-mail/senha + botão Google que já existe dentro do ramo `cloudReady()` de `Auth.openModal()` (linhas ~205–222) deve ser extraído para uma função só, ex. `Auth.authFormHtml()`/`Auth.bindAuthForm()`, porque **dois** lugares agora precisam dele: o modal de conta (reentrada não bloqueante — ver item de sessão perdida abaixo) e a tela cheia do gate de boot (item 1). Isso segue o padrão já usado no projeto (funções pequenas que devolvem HTML reutilizável dentro do mesmo módulo, ex. `Trail.levelHtml()`), evitando ter o mesmo formulário de login escrito duas vezes em dois arquivos.

  **4. Destino do cofre local (`vault.js`)**
  - Decisão: **mantido como está, conceitualmente** — continua fazendo sentido mesmo com conta obrigatória, porque protege contra uma ameaça diferente (dispositivo/navegador comprometido ou compartilhado) da que a conta Supabase protege (credencial de conta). São dois segredos independentes por design (defesa em profundidade), não uma duplicação a eliminar.
  - Única mudança mecânica: remover `STORAGE_KEYS.ACCOUNT` do array `Vault.SENSITIVE_KEYS` (`js/vault.js:31`), consequência direta da remoção da própria chave no item 3.
  - **Risco estrutural encontrado (não pedido, mas bloqueante)**: `Store.clearAll()` (`js/storage.js:107-111`) é chamado pelo botão "Esqueci a senha do cofre" em `app.js:87` e hoje apaga o localStorage inteiro **e** chama `Cloud.deleteAll()` — ou seja, esquecer a senha de um cofre *local* apaga os dados da *conta na nuvem inteira*. Isso já era uma inconsistência entre o texto do `confirm()` ("apaga tudo salvo neste navegador") e o comportamento real; com a nuvem virando fonte de verdade, o dano deixa de ser "perdi meus dados deste navegador" e passa a ser "perdi meus dados permanentemente, em todo lugar, por esquecer uma senha secundária". Decisão: `Store.clearAll()` precisa virar duas operações distintas antes desta RFC ir ao ar — `Store.clearLocalOnly()` (limpa só o cache local + cofre, sem tocar a nuvem; ao recarregar, o boot re-hidrata a partir da nuvem normalmente, já que a sessão de conta continua válida) usada pelo botão "esqueci a senha do cofre"; e uma operação de exclusão de conta de verdade (já registrada como pendência LGPD na Dependência 4 do Product Owner, fora do MVP) para o caso em que o usuário realmente quer apagar tudo da nuvem. Sinalizado para Backend Engineer implementar e Security Specialist validar.

  **5. Modo sem Supabase configurado**
  - Decisão: **não** vira um modo de desenvolvimento com flag própria. `Cloud.isAvailable()` (já existe, `typeof sb !== "undefined" && !!sb`) passa a ser o **único e não contornável** gate — inclusive em desenvolvimento. Novo passo **antes** de qualquer outro gate em `App.init()`: se `!Cloud.isAvailable()`, renderiza uma tela cheia terminal (`#cloudUnavailableScreen`, mesmo padrão `.onboarding-screen`) explicando que o ambiente não está configurado para uso real, e `App.init()` retorna — nada mais roda (nem o gate de autenticação, nem módulo nenhum).
  - Por quê não criar uma flag de "modo dev": uma flag teria que ser desligada manualmente antes de cada deploy — é exatamente o tipo de coisa que um dia fica `true` em produção por esquecimento. Reaproveitar `Cloud.isAvailable()` como sinal único remove essa classe inteira de erro operacional: para desenvolver localmente, basta apontar `js/supabase-config.js` para um projeto Supabase de teste (documentado pelo Documentation/DevOps), não existe um caminho de código separado para "modo local completo" para manter e testar para sempre.
  - Implicação: isso fecha a pendência do Product Owner sobre "modo desenvolvimento explícito" — a resposta é "não precisa, o gate já é a resposta".

  **6. `CITY_LIFE` e chaves de alta frequência de escrita**
  - Decisão: o mecanismo genérico (debounce de 500ms em `Cloud.schedulePush`) é suficiente — **não** precisa de tratamento especial de debounce/lote. O aviso de colisão do item 2 já cobre o cenário que de fato causava perda de dado silenciosa (logar num dispositivo novo/outro enquanto o outro lado tem dados diferentes).
  - Risco residual, documentado e aceito conscientemente (não resolvido nesta RFC): dois dispositivos **logados e ativos ao mesmo tempo**, ambos jogando Cidade Financeira, cada um empurrando seu próprio blob debounced — isso é uma corrida de escrita real, sem heurística de "colisão no login" que a detecte, porque nenhum dos dois nunca passa pelo gate de novo durante a sessão já aberta. `CITY_LIFE`, por reescrever o blob inteiro a cada ação, é a chave mais exposta a essa corrida. Isso é exatamente o mesmo limite que o cabeçalho de `js/cloud.js` já documenta hoje ("não faz merge inteligente entre dispositivos") — a mitigação real é o item 7, não algo para encaixar aqui.

  **7. "Merge inteligente entre dispositivos"**
  - Decisão: **fica para uma RFC seguinte**, não entra nesta.
  - Justificativa (trade-off explícito): merge de verdade exige, no mínimo para as chaves de maior risco (`CITY_LIFE`, e talvez `LESSON_LOG`/`SIMULATOR_LOG`/`POLVIN_LOG`), abandonar o modelo "um blob JSON por chave" em favor de um modelo por linha/evento com resolução por campo ou vetor de versão — isso é uma mudança de modelagem de dados relevante (Database Engineer teria que desenhar isso do zero) e um novo eixo de complexidade no Backend, não um ajuste incremental. Amarrar isso a uma RFC já grande e já reordenada na frente de outras prioridades (nota de sequenciamento no topo) aumenta o risco de atraso de algo que os critérios de aceite desta RFC **não exigem** — o critério 3 pede aviso antes de sobrescrever (resolvido no item 2), não resolução automática de conflito. Ship o MVP de colisão binária agora; abrir RFC de "sincronização concorrente entre dispositivos simultâneos" depois, com dados reais de uso para calibrar se o risco do item 6 se materializa na prática.

  **8. Recuperação de senha**
  - Onde entra: `js/cloud.js` ganha dois métodos novos, mesmo padrão dos já existentes (`signIn`/`signUp`) — `Cloud.resetPasswordForEmail(email)` (chama `sb.auth.resetPasswordForEmail`) e `Cloud.updatePassword(newPassword)` (chama `sb.auth.updateUser({password})`), ambos retornando `{ok, message}` como as demais ações de conta. `js/auth.js` ganha um link/ação "Esqueci minha senha" no formulário extraído no item 3 (`Auth.authFormHtml()`), chamando o novo método de `Cloud`.
  - Peça estrutural adicional (não óbvia, mas necessária): o link de recuperação do Supabase redireciona de volta para o app com um token na URL — `Cloud.init()` precisa **detectar** esse retorno (evento `PASSWORD_RECOVERY` do `sb.auth.onAuthStateChange`, que já está sendo escutado) e expor isso como um estado (`Cloud.recoveryMode`). `App.init()` ganha uma checagem condicional logo após `Cloud.init()`: se `Cloud.recoveryMode`, mostra uma tela cheia de "defina uma nova senha" (`App.ensurePasswordReset()`, mesmo padrão de gate) **antes** do gate de autenticação normal — evita o usuário cair na tela de login logo depois de clicar num link cujo propósito era justamente não precisar da senha antiga. Detalhe de fluxo/copy é do Backend/UX, não desta etapa.

- **Pendências que ficam para as próximas etapas** (não decididas aqui por não serem de arquitetura):
  - Texto/UX exato de cada uma das 4 telas cheias novas (`#cloudUnavailableScreen`, `#authGateScreen`, `#syncCollisionScreen`, tela de reset de senha) — UX/UI Designer.
  - "Confirm email" ligado/desligado — Security Specialist, já registrado como pendência do PO.
  - Exclusão de conta real (LGPD, Edge Function com `service_role`) — fora do MVP, Security/DevOps devem garantir que fica registrada no `ROADMAP.md`.
  - Mecanismo exato de indicador de "falha de escrita" pedido pelo critério de aceite 6: `Cloud.schedulePush`/`pushKey` hoje só fazem `console.warn` em erro — isso não satisfaz "indicador visível + forma de tentar de novo, sem exigir reload". Decisão estrutural: `Cloud` passa a disparar um novo `CustomEvent` (`cloud:sync-error`, `detail: {key, error}`, mesmo padrão de `xp:updated`/`coins:updated`) em vez de só logar; e um segundo evento `account:updated` (nome já existente no projeto, reaproveitado) passa a ser disparado pelo próprio `Cloud` — não mais só por `Auth.setLocalAccount`, que foi removido — sempre que `sb.auth.onAuthStateChange` mudar a sessão (login, logout, ou sessão perdida em segundo plano). Isso cobre o critério 6 sem travar tela nenhuma: leitura continua via `Store.get` (sempre local, nunca depende de rede), só a escrita para a nuvem fica pendente/falha visivelmente. Frontend Engineer implementa o indicador visual a partir desses dois eventos; Backend Engineer implementa o disparo.

#### 0. Três conceitos considerados (tela âncora: `#authGateScreen`)

O maior risco desta etapa é o apontado pelo Product Owner: cadastro obrigatório pode parecer um muro burocrático. Por isso os três conceitos foram desenhados primeiro para essa tela — as outras 3 telas cheias e os 2 estados herdam a linguagem resultante, sem repetir o exercício (são variações de tom da mesma família visual, não telas independentes).

- **Conceito A — Minimalista**: `.onboarding-card` enxuto, POLVIn pequeno (`mascot-md`) só como marca d'água de identidade, título direto ("Entre no PolvIn"), formulário logo abaixo, sem prévia de progresso. Prós: rápido de implementar, não distrai. Contras: não resolve o risco do PO — fica bonito, mas ainda comunica "preencha isto para prosseguir", que é exatamente o "muro" que a RFC pediu para evitar.
- **Conceito B — Gamer** (Clash Royale/Duolingo): o POLVIn "mergulha" na tela (reaproveitando o mesmo idioma visual do `.hero-card-wow` da Início — radial dourado + fala dinâmica) e, se o aparelho já tem XP/moedas salvos localmente, mostra esse número real subindo (`Fx.countUp`) antes de pedir a conta — a mensagem implícita é "isso já é seu, crie uma conta para não perder", não "faça login para começar". Contras: mais estados para o Frontend orquestrar (com progresso vs. sem progresso); se mal calibrado pode soar manipulador — mitigado por ser literalmente verdadeiro (os dados existem e o app não promete nada que não vai cumprir).
- **Conceito C — Premium** (Linear/Apple/Revolut): tipografia grande, muito espaço em branco, POLVIn discreto, copy curta e confiante sobre segurança de dados financeiros, sem gamificação nem confete. Prós: reforça confiança para um app que guarda dados financeiros reais. Contras: sozinho, é genérico — não tem nada que grite "PolvIn" e não "qualquer fintech".

**Recomendação (síntese, não escolha única)**: usar o **Conceito B como espinha dorsal** (é o único dos três que resolve de fato o risco do PO, transformando "faça cadastro" em "garanta o que você já tem"), incorporando a **objetividade do A** (formulário sem etapas extras, sem gamificação forçada nos campos em si — a "prévia" some assim que o formulário aparece) e o **tom de confiança do C** como microcopy de segurança logo abaixo do botão principal. Essa combinação de princípios (não de layouts) é o que vai para as decisões abaixo.

#### Achados

**1. [ALTA] XSS armazenado via user_metadata do Google / e-mail, sem escape em innerHTML** - `js/auth.js:194-199` (renderHeaderChip), `js/auth.js:216-231` (openModal), `js/profile.js:27-35` (renderHeader), `js/app.js:557-562` (renderSessionExpiredChip), `js/leagues.js:130,145-155` (renderLeagues).

O regex client-side em js/auth.js:140 so proibe espaco e @ extra, entao um "e-mail" malicioso poderia teoricamente conter caracteres HTML-significativos. Hoje isso e self-XSS (cada pessoa injeta so na propria tela). Classifico como ALTA e nao BAIXA porque o SDK do Supabase guarda o JWT de sessao em localStorage por padrao - qualquer XSS, mesmo self-XSS, permite roubar esse token e chamar a API REST do Supabase diretamente como o usuario, contornando toda a UI. Alem disso o README ja lista "Ranking/Ligas ao vivo" no roadmap - no dia em que uma tela mostrar nome de OUTRA conta, isso vira XSS cross-user sem que ninguem precise tocar de novo nesse trecho.

Atencao: esse padrao nao escapa aspas, insuficiente para atributo src - construir a tag img via createElement/propriedade .src, nao concatenacao de string. Encaminhar para o Frontend Engineer.

**2. [MEDIA] Decisao "Confirm email": recomendo LIGAR** (estava desligado no teste manual do usuario).

Com "Confirm email" ligado, o Supabase devolve resposta uniforme mesmo para e-mail existente, fechando esse oraculo.
   - Motivo adicional: recuperacao de senha por e-mail e o unico caminho de acesso a uma conta com dados financeiros reais - sem confirmacao, um e-mail digitado errado so e percebido no pior momento (quando a pessoa precisa recuperar a senha).

O ramo needsConfirmation ja existe em Cloud.signUp (js/cloud.js:74-76) e a copia de sucesso ja existe em js/auth.js:152-155 - hoje e codigo morto so porque a chave esta desligada no projeto. Ligar e mudanca de configuracao no painel do Supabase (Authentication -> Providers -> Email -> Confirm email), nao uma PR.

**3. #### Bugs encontrados

**Bug 1 — [CRÍTICA] Tela de colisão (`#syncCollisionScreen`) aparece em toda recarga de página para qualquer usuário já sincronizado, mesmo com dados idênticos entre local e nuvem.**
- **Como reproduzir**: (1) fazer login normalmente numa conta com dados; (2) resolver a colisão inicial (se houver) ou aguardar o boot normal; (3) sem alterar absolutamente nada, recarregar a página (F5). A tela "Encontramos dois progressos diferentes" aparece de novo, bloqueando o boot, exigindo escolher "nuvem" ou "aparelho" outra vez — e volta a aparecer no reload seguinte, indefinidamente. Reproduzido de forma determinística 5 vezes consecutivas neste QA (3 ciclos no dispositivo 1, 1 ciclo no dispositivo 2, todos com `Cloud.session` genuíno, sem nenhuma manipulação de estado entre o resolver e o próximo reload). Confirmação definitiva: logo antes de um dos reloads, uma comparação valor a valor entre as 11 chaves locais e as linhas da tabela `user_data` retornou zero divergências (bytes idênticos) — e mesmo assim a tela de colisão apareceu de novo.
- **Causa raiz (localizada por leitura de código)**: `App.init()` (`js/app.js:29`) chama `this.ensureCloudResolved()` incondicionalmente em todo boot (toda vez que a página carrega com uma sessão válida, não só no primeiro login), que por sua vez chama `Cloud.syncOnLogin()` (`js/cloud.js:170-187`). A detecção de colisão ali é `cloudHasData && localHasData` — presença de dado em ambos os lados, não divergência de conteúdo. Uma vez que a primeira sincronização bem-sucedida acontece, a nuvem sempre tem uma ou mais linhas e o cache local sempre tem uma ou mais chaves (é o cache persistente do próprio navegador) — logo essa condição é verdadeira para praticamente todo boot subsequente de um usuário que já sincronizou alguma vez, para sempre, independentemente de os dados terem mudado ou não.
- **Impacto**: quebra o uso normal do dia a dia do app (qualquer F5/reabrir aba força uma decisão bloqueante e sem opção de cancelar, por decisão de design do próprio Software Architect nesta RFC, item 2, "sem opção de cancelar/decidir depois"); e, mais grave, desenha o usuário a clicar sem ler um aviso cujo propósito inteiro (critério de aceite 3) é evitar perda de dado — no dia em que houver uma divergência real (ex.: um push que ainda não terminou o debounce de 500ms), o hábito adquirido de "clicar em qualquer um dos dois botões para o app voltar a funcionar" é exatamente o cenário que este mecanismo foi desenhado para prevenir.
- **Sugestão**: `Cloud.syncOnLogin()` precisa distinguir "primeiro contato entre este dispositivo e esta conta" (quando a checagem de colisão faz sentido) de "reload de rotina de uma sessão já resolvida" (quando não deveria rodar de novo, ou deveria comparar conteúdo, não só presença). Um caminho possível, sem reabrir a decisão "sem heurística de timestamp" do Software Architect (que era sobre timestamp como critério de quem vence, não sobre se checar): comparar o conteúdo das chaves locais contra as linhas retornadas antes de declarar colisão — só sinalizar `case: "collision"` se houver alguma chave realmente divergente, não pela mera coexistência de dados nos dois lados. Encaminhar para o Backend Engineer (lógica em `js/cloud.js`), com o Software Architect revisando a mudança de contrato de `syncOnLogin()` por afetar uma decisão já registrada nesta RFC.

**Bug 2 — [MÉDIA] Balão de tooltip fica órfão na tela depois que o chip de "sincronização pendente" se remove do DOM após um retry bem-sucedido.**
- **Como reproduzir**: provocar `cloud:sync-error` (chip "Sincronização pendente" aparece no header, com dica via `js/tooltip.js`); clicar no chip. O clique simultaneamente (a) aciona `Tooltip.show()` (o chip tem classe `.tip-trigger`) e (b) aciona a lógica de retry do próprio `App`, que em caso de sucesso remove o chip do DOM (comportamento documentado na etapa do Frontend Engineer: "chip se remove do DOM, não deixa vão reservado"). - **Sugestão**: em `js/tooltip.js`, chamar `Tooltip.hide()` proativamente se o gatilho atual for removido do DOM — ou, mais simples, no ponto em `js/app.js` que remove o chip com sucesso, chamar `Tooltip.hide()` explicitamente antes do `.remove()`. Encaminhar para o Frontend Engineer.

#### Revisão do Software Architect sobre o Bug 1 (pós-QA)

**Diagnóstico confirmado.** Reli minha própria decisão no item 2 desta etapa (`### 2. Software Architect`) e concordo com a causa raiz apontada pelo QA: "binário, sem heurística de timestamp" (item 2) foi uma decisão sobre **quem vence** um conflito, não sobre **se existe** conflito — a implementação de `syncOnLogin()` (`js/cloud.js:170-187`) colapsou as duas perguntas na mesma condição (`cloudHasData && localHasData`), que é presença, não divergência. Isso não reabre o item 7 ("merge inteligente entre dispositivos" continua fora do MVP, sem resolução automática de conflito real) nem o item 6 (risco residual de dois dispositivos simultâneos continua aceito e documentado) — é uma correção de um bug de implementação numa decisão que, na intenção original, já devia ter sido "divergência de conteúdo", não "coexistência de dados".

**1. Aceito a sugestão do QA como contrato oficial.** `syncOnLogin()` só declara `case: "collision"` se pelo menos uma chave presente **nos dois lados** tiver conteúdo diferente. Chave que existe só de um lado não é conflito — é dado que o outro lado ainda não tem, e resolve sozinho (mesmo espírito dos casos `cloud-empty`/`local-empty` já existentes, que também nunca precisaram de UI).

**2. Caso misto (chaves só-de-um-lado + chave divergente ao mesmo tempo): continua sendo colisão, decisão confirmada, sem mudança.** Não vale a pena resolver as chaves só-de-um-lado automaticamente "enquanto isso" — criaria um terceiro comportamento (aplicar parte da união agora, esperar decisão do usuário para a outra parte) que multiplica estados possíveis de `applyCloudWins`/`applyLocalWins` sem que nenhum critério de aceite peça isso. Se há qualquer divergência real, a tela de colisão já cobre a união inteira quando o usuário escolhe um lado (`applyCloudWins` limpa e reaplica tudo; `applyLocalWins` empurra tudo e apaga o que sobrou) — as chaves só-de-um-lado acabam resolvidas de qualquer forma, só que dentro do fluxo que já existe, sem precisar de um terceiro caminho de código.

**3. Custo confirmado como desprezível.** As ~41 chaves de `STORAGE_KEYS` já estão em mãos no momento da comparação — o local via `localStorage.getItem` (já lido por `hasLocalData()`) e o remoto via `rows`, retornado por `fetchRemoteRows()` que já roda incondicionalmente no início de `syncOnLogin()` hoje. Não há chamada de rede nova, nem chamada por chave — é uma iteração em memória sobre no máximo 41 pares, uma vez por boot-com-sessão (nunca durante a sessão já aberta, conforme o comentário original do método). Sem impacto de performance perceptível.

**4. Formato da comparação: serialização canônica com chaves ordenadas recursivamente, não `JSON.stringify` direto.** `JSON.stringify` simples falharia por motivo errado: dois objetos com o mesmo conteúdo, mas escritos em ordens diferentes (ex.: `{a:1,b:2}` local vindo de uma escrita antiga do app vs. `{b:2,a:1}` retornado pelo driver do Postgres para a mesma coluna `jsonb`), produzem strings diferentes e gerariam falso positivo de divergência — exatamente o tipo de "colisão fantasma" que estamos corrigindo, só que reintroduzido de outra forma. Contrato: uma função `_stableStringify(value)` que ordena chaves de objetos (`Object.keys(value).sort()`) antes de serializar, recursivamente, e preserva a ordem de arrays (ordem em array é dado, não é estrutura de objeto — ex. um array de eventos de log não pode ter sua ordem alterada pela normalização). JSON malformado do lado local (`JSON.parse` lança exceção) é tratado como divergente por padrão — não dá para provar igualdade de algo ilegível, e a postura de risco desta RFC já é "na dúvida, avisa" (critério de aceite 3), não "na dúvida, assume igual".

**5. Confirmado: não precisa de timestamp/versionamento.** Esta correção é inteiramente sobre content-equality (as chaves em comum têm ou não o mesmo valor), nunca sobre "qual lado é mais recente" — a decisão original do item 2 ("sem heurística de timestamp para decidir quem vence") permanece intacta e não é tocada por este fix. `updated_at` na tabela `user_data` continua existindo só para fins informativos/auditoria, não entra em nenhuma decisão de `syncOnLogin()`.

**Contrato exato para o Backend Engineer implementar em `js/cloud.js`:**

```js
/* Serialização canônica: ordena chaves de objetos recursivamente antes de
   comparar, para que diferença de ORDEM de serialização entre o localStorage
   (escrito pelo próprio app) e o retorno jsonb do Postgres (via driver do
   Supabase) nunca seja confundida com diferença de CONTEÚDO. Arrays mantêm
   a ordem original — ordem em array é dado. */
_stableStringify(value) {
  if (Array.isArray(value)) {
    return "[" + value.map((v) => this._stableStringify(v)).join(",") + "]";
  }
  if (value && typeof value === "object") {
    return "{" + Object.keys(value).sort()
      .map((k) => JSON.stringify(k) + ":" + this._stableStringify(value[k]))
      .join(",") + "}";
  }
  return JSON.stringify(value);
},

/* true só se existir ao menos uma chave presente NOS DOIS LADOS (local e
   nuvem) com conteúdo diferente. Chave que só existe de um lado nunca conta
   como divergência aqui — isso não é colisão, é união (ver syncOnLogin). */
_hasDivergentCommonKeys(rows) {
  const remoteByKey = new Map(rows.map((r) => [r.key, r.value]));
  return Object.values(STORAGE_KEYS)
    .filter((key) => key.indexOf("if_vault_") !== 0)
    .some((key) => {
      const raw = localStorage.getItem(key);
      if (raw === null || !remoteByKey.has(key)) return false; // só existe de um lado: não é conflito
      let localValue;
      try {
        localValue = JSON.parse(raw);
      } catch (e) {
        return true; // JSON local ilegível: não dá pra provar igualdade -> trata como divergente
      }
      return this._stableStringify(localValue) !== this._stableStringify(remoteByKey.get(key));
    });
},

async syncOnLogin() {
  const rows = await this.fetchRemoteRows();
  const cloudHasData = rows.length > 0;
  const localHasData = this.hasLocalData();

  if (!cloudHasData && !localHasData) return { case: "both-empty", rows };
  if (!cloudHasData && localHasData) {
    await this.pushAllLocal();
    return { case: "cloud-empty", rows };
  }
  if (cloudHasData && !localHasData) {
    this.hydrateLocalFrom(rows);
    return { case: "local-empty", rows };
  }

  // cloudHasData && localHasData: só é colisão de verdade se alguma chave
  // presente nos dois lados tiver conteúdo diferente (item 1 desta revisão).
  if (this._hasDivergentCommonKeys(rows)) {
    return { case: "collision", rows };
  }

  // Chaves em comum são idênticas; chaves só de um lado (se houver) não são
  // conflito — resolve sozinho, sem UI, unindo os dois lados. Idempotente
  // para as chaves já iguais (hydrate/push não mudam nada nelas).
  this.hydrateLocalFrom(rows);
  await this.pushAllLocal();
  return { case: "reconciled", rows };
},
```

**Novo valor de enum**: `case` passa a ter 5 valores possíveis (`"both-empty" | "cloud-empty" | "local-empty" | "reconciled" | "collision"`), um a mais que o contrato original do item 2 (`"cloud-empty" | "local-empty" | "both-empty" | "collision"`). `"reconciled"` é o caso do Bug 1: ambos os lados têm dado, nenhuma chave em comum diverge.

**Confirmado: nenhuma mudança em `js/app.js`.** `App.ensureCloudResolved()` (`js/app.js:314-316`) já testa `if (result.case !== "collision") return true;` — ou seja, qualquer `case` novo que não seja `"collision"` já resolve o gate sem UI, sem precisar tocar no Frontend. O novo caso `"reconciled"` cai automaticamente nesse ramo existente. Nenhuma mudança de schema no Supabase (Database Engineer já confirmado no item 2 original — segue key/value, `updated_at` não entra na decisão).

**Resumo para o Backend Engineer (~100 palavras):** Em `js/cloud.js`, substitua a condição `cloudHasData && localHasData → collision` por uma checagem de conteúdo. Adicione `_stableStringify(value)` (ordena chaves de objeto recursivamente, mantém ordem de array) e `_hasDivergentCommonKeys(rows)` (compara, chave a chave, só as chaves presentes local E remotamente; ignora chaves só-de-um-lado; JSON local corrompido conta como divergente). Em `syncOnLogin()`, quando `cloudHasData && localHasData`: se `_hasDivergentCommonKeys(rows)` for true, retorne `{case: "collision", rows}` (comportamento inalterado); senão, rode `hydrateLocalFrom(rows)` + `await pushAllLocal()` e retorne `{case: "reconciled", rows}`. Nenhuma mudança em `app.js` é necessária. Sem chamada de rede nova, sem timestamp, sem tocar nos itens 6/7 desta RFC. #### Implementação do fix do Bug 1 (Backend Engineer)

Implementado exatamente o contrato definido pelo Software Architect em `js/cloud.js`, sem nenhum desvio de nome, assinatura ou comportamento:

**1. `_stableStringify(value)`** — adicionada logo após `hasLocalData()`. Serializa recursivamente: `Array.isArray(value)` mantém a ordem original dos elementos (`"[" + value.map(...) .join(",") + "]"`); objeto genérico ordena as chaves com `Object.keys(value).sort()` antes de montar `"{" + ... + "}"`; qualquer outro tipo (string, number, boolean, null, undefined) cai no `JSON.stringify(value)` padrão, que já é determinístico para esses casos.

**2. `_hasDivergentCommonKeys(rows)`** — adicionada logo em seguida. Monta `remoteByKey` como `Map` a partir de `rows` (retorno de `fetchRemoteRows()`, já disponível sem chamada de rede nova). Itera `Object.values(STORAGE_KEYS)` excluindo `if_vault_*` (mesmo filtro já usado em `hasLocalData()`/`applyCloudWins()`, mantendo o padrão do arquivo) e usa `.some(...)`: se a chave não existe localmente (`raw === null`) ou não existe na nuvem (`!remoteByKey.has(key)`), retorna `false` para essa chave (não é conflito, é união). Se `JSON.parse(raw)` lançar exceção, retorna `true` (postura "na dúvida, avisa", conforme decisão do Architect). Caso contrário, compara `_stableStringify(localValue) !== _stableStringify(remoteByKey.get(key))`.

**3. `syncOnLogin()` revisado** — reescrito seguindo a ordem exata do pseudocódigo do Architect: `both-empty`, `cloud-empty` (push), `local-empty` (hydrate) tratados primeiro e sem alteração de comportamento; o ramo `cloudHasData && localHasData` agora chama `_hasDivergentCommonKeys(rows)` — se `true`, retorna `{case: "collision", rows}` (comportamento antigo preservado para colisão real); se `false`, executa `hydrateLocalFrom(rows)` seguido de `await pushAllLocal()` e retorna `{case: "reconciled", rows}`, o novo caso. Nenhuma alteração em `js/app.js`: confirmado por leitura que `App.ensureCloudResolved()` testa `result.case !== "collision"` genericamente, então `"reconciled"` já cai no caminho sem UI sem precisar de nenhum ajuste no Frontend.

**Verificação manual (sem Node.js disponível neste ambiente, mesma limitação já registrada pelo QA e pelo Frontend Engineer nesta RFC)** — revisão de balanceamento de chaves/parênteses linha a linha em `js/cloud.js` (confirmado: toda função nova abre e fecha corretamente, incluindo os dois `if`/`try-catch` aninhados dentro de `_hasDivergentCommonKeys`) e simulação mental de 3 casos, todos usando o mesmo `_stableStringify`/`_hasDivergentCommonKeys` que vai rodar em produção:

- **Caso 1 — idêntico nos dois lados** (`local: {if_xp: 100}`, `remote rows: [{key:"if_xp", value:100}]`, nenhuma outra chave presente em nenhum lado): para `if_xp`, `raw` não é `null` e `remoteByKey.has("if_xp")` é `true`; `_stableStringify(100) === _stableStringify(100)` → `"100" === "100"`, sem divergência; nenhuma outra chave de `STORAGE_KEYS` está presente em nenhum dos dois lados, então `.some(...)` nunca encontra `true` → `_hasDivergentCommonKeys` retorna `false` → `syncOnLogin()` cai no ramo `reconciled`. Correto: é exatamente o cenário do Bug 1 (reload sem mudança nenhuma).
- **Caso 2 — só uma chave a mais de um lado, resto idêntico** (local tem `if_xp: 100` e também `if_coins: 50` que ainda não foi sincronizado; nuvem só tem `if_xp: 100`): para `if_xp`, mesma comparação do Caso 1, sem divergência. Para `if_coins`, `remoteByKey.has("if_coins")` é `false` → retorna `false` para essa chave antes mesmo de tentar comparar valor (curto-circuito do `||`). Nenhuma chave gera `true` → `_hasDivergentCommonKeys` retorna `false` → `reconciled`, que faz `hydrateLocalFrom` (não altera `if_coins`, que não veio da nuvem) seguido de `pushAllLocal()` (sobe `if_coins: 50` para a nuvem) — o dado só-de-um-lado se resolve sozinho como união, sem tela de colisão. Correto.
- **Caso 3 — uma chave com valor diferente nos dois lados** (local `if_xp: 100`, nuvem `if_xp: 105`): `raw` não é `null`, `remoteByKey.has("if_xp")` é `true`, `_stableStringify(100) !== _stableStringify(105)` → `"100" !== "105"` é `true` → `.some(...)` retorna `true` no primeiro `true` encontrado → `_hasDivergentCommonKeys` retorna `true` → `syncOnLogin()` retorna `{case: "collision", rows}`, preservando a tela de colisão exatamente quando há divergência real. Correto.

Verificado também o caso de ordenação de chaves (a razão de existir `_stableStringify` em vez de `JSON.stringify` direto): objeto local `{a: 1, b: 2}` (`JSON.stringify` → `'{"a":1,"b":2}'`) vs. objeto remoto vindo do driver como `{b: 2, a: 1}` (`JSON.stringify` → `'{"b":2,"a":1}'`, diferente por ordem) — com `_stableStringify`, ambos ordenam as chaves via `Object.keys(value).sort()` antes de montar a string, então os dois produzem `'{"a":1,"b":2}'`, iguais, sem falso positivo. Confirmado também que um array (ex.: histórico de eventos) não tem suas posições reordenadas pela função — só o objeto que o contém, se houver, tem suas chaves ordenadas.

**Resumo para o QA Engineer (~100 palavras):** O fix do Bug 1 foi implementado em `js/cloud.js` exatamente conforme o contrato do Software Architect: `_stableStringify()` e `_hasDivergentCommonKeys()` adicionadas, `syncOnLogin()` reescrito para só declarar `collision` quando há divergência real de conteúdo em alguma chave comum, retornando `reconciled` quando os dois lados têm dado mas nada diverge. Nenhuma mudança em `js/app.js` foi necessária (confirmado por leitura). Lógica verificada manualmente linha a linha (balanceamento de sintaxe) e com 3 casos mentais (idêntico, chave só-de-um-lado, chave divergente) — todos produzem o resultado esperado.
